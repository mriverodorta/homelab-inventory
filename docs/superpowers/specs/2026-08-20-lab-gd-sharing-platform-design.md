# lab.gd Sharing Platform Design

**Status:** Approved design

**Date:** 2026-08-20

**Repositories:**

- Public application: `ServerSpecsInventory`
- Private sharing service: `HomelabInventoryShare`
- Public Registry dependency: `ServerSpecsInventoryRegistry`
- Public npm organization: `@homelab-inventory`

## Purpose

`lab.gd` is a public-facing, read-only sharing service for deliberately selected
Homelab Inventory content. It lets an installation publish a canvas, Systems
view, selected workbook views, or a whole project without exposing the private
application or requiring a `lab.gd` account.

The first release supports full-page shares, restricted embeds, immutable and
replaceable publication, optional password protection, expiration, social
previews, privacy review, abuse reporting, lightweight analytics, Registry-aware
payload reduction, and optional GitHub account claiming.

It does not provide collaborative editing, arbitrary uploads, share rollback,
comments, reactions, public profiles, galleries, search, or forking. Comments
and reactions may be represented as disabled or "Coming soon" interface states.

## Product Boundaries

Homelab Inventory remains the source of truth and owns all editable inventory,
projects, workspaces, assignments, connections, routing, telemetry, tags, custom
fields, and Registry-link state.

`lab.gd` receives only the content explicitly included in a publication preview.
It stores immutable share revisions and exposes read-only viewer projections.
It cannot mutate or query the private installation.

The Registry remains the source of signed public template definitions. `lab.gd`
mirrors the exact historical template revisions referenced by shares and never
resolves a linked item to the latest Registry revision.

## Repository And Package Ownership

The `HomelabInventoryShare` GitHub repository is private. Its deployment source,
database schema, moderation tools, analytics, and account-management code remain
private.

Reusable read-only behavior is extracted from Homelab Inventory and published
from the public repository under the `@homelab-inventory` npm organization:

- `@homelab-inventory/share-contract`: Zod schemas, canonical serialization,
  content hashing, protocol negotiation, fixtures, and compatibility rules.
- `@homelab-inventory/viewer-model`: read-only Systems, Canvas, workbook,
  selection, deep-link, formatting, and projection logic.
- `@homelab-inventory/viewer-react`: read-only Systems, Canvas, inspector,
  workbook tabs, and embed viewer components.

The private service pins exact package versions. It must not copy application
components or import application persistence, editing, agent, authorization, or
Registry credential modules.

Homelab Inventory owns the reusable rendering packages. `lab.gd` owns the public
shell, publication API, storage, GitHub authentication, analytics, moderation,
social previews, lifecycle workers, and deployment.

## Share Model

### Share Mutability

A share is one of:

- **Immutable:** its activated content never changes.
- **Replaceable:** a new immutable revision can atomically replace the active
  revision while preserving the share URL.

Replaceable shares support:

- **Synchronized:** relevant local changes schedule a publication after a
  one-minute trailing debounce.
- **Manual:** local changes set `manual-update-available`; the user publishes
  with an Update share command.

No public rollback interface is included. Historical revisions are retained only
as required for integrity, active requests, retention, and safe garbage
collection; they are not selectable by viewers.

### Visibility

A share is one of:

- **Public:** anonymously viewable and indexable.
- **Unlisted:** anonymously viewable by URL and served with `noindex`.
- **Password protected:** content is unavailable until the password challenge
  succeeds.

Password-protected routes must not leak title, description, preview image,
manifest, object names, counts, analytics, or other content. They return a
generic password page and a generic social preview.

### Share Identifiers

Share IDs are cryptographically random, generated by `lab.gd`, non-sequential,
and never user-selectable. A generated ID remains permanently reserved.

After expiration or inactivity deletion, the content is purged and a minimal
tombstone retains the ID, ownership binding, status, and expiration timestamp.
The same installation identity or a GitHub account that had claimed the share
may reactivate the same ID. An unrelated installation receives a new ID.

## Content Selection

A share manifest can include one view, multiple views, or every eligible view in
a project. Initial supported view types are:

- `systems`
- `canvas`

The contract is extensible to `rack`, `network`, `services`, and future view
types through independently versioned view schemas. A whole-project share
reproduces the selected workbook tab order and tab presentation.

Safe presentation data is eligible by default: selected view configuration,
sanitized names, generic definitions, visual placement, ports, connections, and
allowed item details.

The following are excluded by default and cannot be silently included:

- Serial numbers
- IP and MAC addresses
- Agent identity and credentials
- Heartbeat and telemetry history
- Registry enrollment identity and credentials
- Authentication, authorization, and audit data
- Internal database IDs that are not required by the share contract
- Private metadata
- Secrets, tokens, passwords, and arbitrary files

Tags and custom fields are individually selectable and default to excluded.

Before the first publication and after selection changes, the application opens
a mandatory privacy preview in a new tab. The preview renders the exact outgoing
payload and viewer, reports included views, items, connections, Registry
references, custom-field definitions, and exclusions, and must succeed before
publication is enabled.

## Systems Resource Snapshot

A Systems share may include a one-time resource snapshot containing current CPU,
memory, and storage usage plus `capturedAt`. It includes no heartbeat history,
raw agent payload, host identity, or live telemetry stream.

Automatic share synchronization never refreshes resource snapshots. An explicit
Update resource snapshot command captures all included systems atomically. The
viewer labels the capture time and does not imply that the values are live.

## Registry-Linked Content

Registry-linked items do not duplicate their complete public definition in share
payloads. They include:

- exact `templateKey`
- exact `templateRevision`
- exact `contentHash`
- sanitized local instance data
- explicitly allowed local overrides

Custom and detached items include their complete sanitized custom definition.

`lab.gd` mirrors signed historical Registry artifacts and stores each unique
`(templateKey, templateRevision, contentHash)` definition once. It resolves only
the revision referenced by the local item. A newer Registry revision that the
user has not applied cannot affect an existing share.

The public inspector may identify the item as Registry verified and show its
exact revision. It must not expose unrelated update-available state.

If an exact historical Registry definition is unavailable or fails signature or
hash verification, activation fails without replacing the currently active
share revision.

## Content-Addressed Publication Protocol

Each view is serialized canonically and addressed by SHA-256. Publication uses:

1. The application builds and validates the local share manifest.
2. The application sends the signed manifest and view hashes.
3. `lab.gd` returns the hashes it does not already possess.
4. The application uploads only missing compressed blobs.
5. `lab.gd` authenticates the installation, prevents replay, enforces compressed
   and expanded limits, decompresses within a bounded environment, validates
   Zod schemas and semantic references, resolves Registry references, and
   verifies hashes.
6. `lab.gd` creates an immutable revision and atomically changes the share's
   active-revision pointer.
7. Asynchronous workers generate the social preview and compact analytics
   projections.

An update failure leaves the previous public revision available. Blobs are
deduplicated across revisions and shares. Garbage collection deletes an
unreferenced blob only after a quarantine period and a fresh reference audit.

Initial limits are:

- 25 active shares per installation
- 10 MB maximum expanded share size
- 2 MB maximum compressed share size
- one successful update per share per minute
- bounded installation, IP, and global request rates
- bounded password attempts
- no arbitrary HTML, scripts, images, or file uploads

## Protocol Negotiation

Compatibility is based on:

- `shareContractVersion`
- per-view schema versions
- supported view types
- renderer feature flags

Application SemVer is diagnostic and is not the compatibility contract. The
application must block publication with a clear error when `lab.gd` cannot
consume every selected view or required feature.

Unknown fields are rejected where the signed contract requires a closed schema.
Older supported fields are migrated only through explicit, versioned boundary
adapters. Unsupported versions fail rather than being flattened or discarded.

## Installation Identity And Authentication

Sharing uses an identity independent from Registry enrollment:

```text
/data/sharing/installation-instance.json
/data/sharing/installation-private-key
/data/sharing/installation-credentials.json
```

The installation UUID and Ed25519 private key are created once, owned by the
application UID, and stored with mode `0600`. They are included in complete and
selectable sharing-identity backups. Environment synchronization must never copy
them between installations.

Enrollment uses signed challenge and activation. Authenticated publication
requests include a short-lived scoped token, timestamp, nonce, request body
hash, and Ed25519 signature. Nonces are single-use and timestamps have a bounded
acceptance window.

Key rotation is authenticated. The current key and credentials remain active
until replacement succeeds. Identity conflicts enter a persisted
`recovery-pending` state, stop publication, retain one replacement key, and do
not create retry loops or duplicate logical installations.

Demo mode never enrolls, publishes, rotates, recovers, or claims shares.

## Optional GitHub Account Claiming

Publishing does not require a `lab.gd` account. A user may later connect a GitHub
account using Better Auth and a short-lived device/claim flow. The local backend
maintains only a temporary outbound connection while the claim is pending.

One GitHub account may claim multiple installations. A claimed account can
manage its shares but cannot query the private installation or receive private
inventory data.

Local authorization uses static permissions and existing custom roles:

- `sharing.configure`
- `sharing.publish`

Owner and Administrator receive both by default. Editors receive neither unless
granted through a custom role.

## Password Protection

The local installation does not store the share password. It transmits the
password once over HTTPS when setting or replacing protection.

`lab.gd` hashes the password with Bun Argon2id using a unique salt and a
versioned server-side pepper loaded from Infisical. PostgreSQL stores only the
PHC hash and pepper version. Verification uses `Bun.password.verify` and
constant-time library behavior. A password cannot be recovered; it can only be
replaced.

Successful full-page verification creates one short-lived opaque
`__Host-labgd_viewer` cookie with `Path=/`, `HttpOnly`, `Secure`,
`SameSite=Lax`, and no `Domain`. It identifies a server-side viewer session;
separate grants bind that session to numeric share and active-revision IDs.
Every protected request rechecks the applicable grant, so the host-wide path
does not grant cross-share access and one browser session can unlock multiple
shares independently.

Protected cross-origin embeds do not rely on the Lax cookie. After password
verification they receive a separate short-lived bearer capability bound to the
numeric share, active revision, and exact allowlisted embedding origin. Exact
origin means normalized HTTPS scheme, hostname, and any non-default port.

The protected embed snippet includes a versioned parent bridge. A generic iframe
shell creates a one-time nonce, performs a nonce-bound `postMessage` handshake,
and reads the browser-provided `MessageEvent.origin`. The parent bridge attests
the nonce to Hono, whose browser-controlled `Origin` header must match the exact
share allowlist. Password verification consumes that server attestation and
requires the iframe-observed origin to match before issuing the capability. CSP
`frame-ancestors` remains the primary browser enforcement. Missing, opaque,
HTTP, mismatched, or unallowlisted origins fail closed. `Referer` is never an
authorization proof.

The iframe keeps the capability only in memory and sends it only in the
Authorization header. It never enters a URL, cookie, browser storage, log,
referrer, analytics record, or parent-window message, and reloading requires
verification again.

## Viewer And Embed

Full-page shares use `/s/{shareId}`. They provide:

- a compact `lab.gd` utility header
- a restrained title and description region
- the interactive read-only viewer
- selected workbook tabs
- deep linking and centering
- optional comments and reactions sections, initially shown as Coming soon
- report-abuse and compact share actions

Deep links support selected view, item, and connection without exposing private
database identifiers:

```text
?view=<public-view-id>&item=<public-object-id>
?view=<public-view-id>&connection=<public-connection-id>
```

Embed shares use `/e/{shareId}` and prioritize the viewer. A functional header
shows the title, expandable description, read-only reaction/comment counts when
enabled, and Open on lab.gd. It does not host comments.

Embedding is disabled by default. When enabled, exact HTTPS origins are
allowlisted and enforced with `Content-Security-Policy: frame-ancestors`.
Public and unlisted shares may explicitly permit all origins. Password-protected
shares never permit wildcard embedding.

The embed configurator controls initial view, focused object, inspector,
workbook tabs, title expansion, theme, fullscreen, allowed origins, and suggested
dimensions or aspect ratio.

The interface follows the Homelab Inventory design system and Impeccable
guidelines: quiet operational layout, limited badges, no decorative card stacks,
no oversized marketing composition, consistent spacing, clear command icons,
and responsive overflow behavior.

## Social Preview, QR, And Share Actions

A static social preview is generated asynchronously for each activated revision,
stored by content hash, and reused until content changes. A generic preview is
served while rendering is pending or when the share is protected.

Initial compact actions are Copy link, Copy embed, Open, Download social image,
and Show QR code.

## Expiration And Retention

A share can be indefinite, expire after a duration, or expire at a fixed UTC
date and time.

Duration presets are one hour, 24 hours, seven days, 30 days, and 90 days. A
custom duration may be between one hour and one year. A successful publication
resets duration-based expiration. It does not move fixed-date expiration.

Expired content is purged and the route displays an expired state instead of a
404. The permanent ID tombstone remains.

Active content is also purged after one year without a qualified viewer load.
The baseline is `lastQualifiedViewerLoad ?? firstActivatedAt`. Only a successful
full-page or embed content load resets the timer. Owner updates, synchronization,
settings changes, crawlers, social previews, health checks, failed password
attempts, and analytics requests do not reset it.

When local sharing is disabled:

- Unclaimed shares enter a 30-day grace period and are then purged.
- Claimed shares offer Keep online or Disconnect and unpublish.

The user may immediately unpublish or delete from either the local installation
or a claimed account dashboard.

## Analytics And Abuse Reporting

The owner may view:

- total qualified views
- approximate unique daily visitors
- full-page and embed counts
- referring hostname only
- last viewed timestamp

The system does not retain raw IP addresses, full referrers, user-agent history,
geographic profiles, or browser fingerprints. Approximate visitor identifiers
use a daily derived HMAC key so they cannot be correlated across days.

Hono captures an external referring hostname only from the initial full-page or
embed HTML request. It parses and bounds the hostname server-side, discards the
scheme, port, and all other URL parts, associates it through a short-lived
one-time analytics bootstrap token, and never accepts attribution later from
browser JavaScript. This hostname-only value and token are separate from the
exact-origin embed authorization context and never cross between those stores.

Only client-confirmed initial content loads count as qualified views. This is an
abuse-resistant product metric rather than proof that a human viewed the
content. Automated social-preview and health requests do not count.

Abuse reporting is available at launch. Reports enter a private moderation
queue. Reporters do not need access to share-owner data. The moderation system
uses stable reason codes, sanitized optional details, immutable events, bounded
submission rates, and explicit disposition history.

## Local Publication Experience

The sharing settings and publication flow include:

- global enablement and installation enrollment state
- optional Connect my lab.gd account
- title and description
- selected views or entire project
- immutable or replaceable
- synchronized or manual update mode
- public, unlisted, or password-protected visibility
- expiration controls
- resource-snapshot inclusion and refresh
- individually selected tags and custom fields
- comments and reactions enablement
- embed permission and origin allowlist
- a persistent summary of what leaves the installation
- Open preview and one primary Publish share command

Publication state is delivered to the application through SSE:

- Synced
- Changes pending
- Publishing
- Manual update available
- Failed
- Expired
- Grace period
- Unpublished

The public viewer loads the shell, title metadata, manifest, and initial view
first. Other views and inspectors load on demand.

## Private Service Architecture

The private repository uses a Bun workspace:

```text
apps/api
apps/web
packages/database
packages/domain
packages/registry-mirror
packages/observability
workers/renderer
workers/lifecycle
workers/analytics
```

The API uses Hono, Zod, Drizzle, PostgreSQL, and the shared public packages. The
web application uses React, Vite, shadcn/ui, Lucide, and the shared viewer React
package.

PostgreSQL stores metadata, revisions, ownership, hashes, analytics aggregates,
reports, operations, and tombstones. Content-addressed blobs and social previews
use a private SkyBolt filesystem store referenced by hash.

Public API, renderer, lifecycle, analytics, and Registry-mirror workers use
separate PostgreSQL roles and separate secrets. The renderer is isolated in its
own hardened Chromium container. The API and web images use distroless runtimes
where compatible.

## Deployment And Operational Safety

The service runs on SkyBolt behind Cloudflare Tunnel. PostgreSQL has no host
port. Watchtower is disabled. Images and dependencies are pinned. All normal
services run as non-root with a read-only root filesystem, all capabilities
dropped, `no-new-privileges`, and bounded `noexec,nosuid,nodev` temporary
storage.

A narrowly privileged one-shot storage initializer establishes filesystem
ownership. Ordered transactional migrations complete before dependent services
start. Configuration fails closed, including rejecting simultaneous direct and
file-based secret values.

Durable background operations use:

- idempotency keys
- bounded attempts and backoff
- worker leases and heartbeats
- optimistic resource revisions
- `FOR UPDATE SKIP LOCKED`
- explicit state transitions
- sanitized append-only events
- PostgreSQL transactional outbox and `LISTEN/NOTIFY`
- periodic reconciliation only for recovery

Health and readiness are separate. Readiness checks PostgreSQL, active schema,
object storage, and required Registry-mirror state without invoking expensive
rendering.

Matched backups include PostgreSQL, content blobs, social previews, deployment
metadata, checksums, and source revision. Restore validation checks hashes,
archive traversal, database structure, and object references in an isolated
temporary database and object tree before cutover. SkyArk is accessed only
through the established SkyBolt backup workflow.

## Failure Behavior

- Unsupported contracts are rejected before upload.
- Invalid signatures, expired timestamps, and reused nonces are rejected without
  revealing installation state.
- Missing blobs leave the operation staged and never change the active revision.
- Registry hash or signature failures block activation.
- Renderer failure keeps content available with a generic social preview.
- Analytics failure cannot block viewer delivery.
- Lifecycle cleanup is idempotent and requires a current revision check before
  purging.
- GitHub authentication failure does not affect installation-owned publication.
- Identity conflict enters recovery pending and stops writes without deleting
  the current key.

## Testing And Acceptance

### Shared Packages

- Canonical serialization and hashing are deterministic across Node and Bun.
- Contract fixtures round-trip without unknown-field loss.
- Every supported view has version negotiation and unsupported-version tests.
- Viewer projections match Homelab Inventory for Systems and Canvas fixtures.
- Deep links, centering, selection, and lazy view loading are deterministic.

### Homelab Inventory

- Preview payload exactly matches the published payload.
- Excluded private fields cannot cross the publication boundary.
- Registry-linked and custom items produce the correct representation.
- Synchronized publication debounces and manual publication does not send
  automatically.
- Resource snapshots change only through the explicit command.
- Identity backup, restore, restart, rotation, recovery, and environment-sync
  behavior preserve installation boundaries.
- Demo mode performs no sharing network operation.

### lab.gd

- Compressed and expanded limits resist decompression bombs.
- Signature, nonce, timestamp, idempotency, rate, and ownership checks fail
  closed.
- Activation is atomic and preserves the previous revision on failure.
- Password-protected routes leak no share content before authentication.
- Embed CSP accepts only configured origins.
- Expiration, grace, inactivity purge, reactivation, and permanent tombstones are
  deterministic and idempotent.
- Daily analytics cannot correlate a visitor across days.
- Abuse reports do not disclose owner or installation information.
- Registry historical definitions are exact and signature verified.

### Deployment

- Lint, tests, production builds, migrations, container smoke tests, and
  vulnerability scans pass.
- Every runtime image has zero known vulnerabilities at every severity.
- PostgreSQL remains unexposed.
- Restart and worker retry produce no duplicate share, revision, blob, account
  claim, analytics count, or lifecycle action.
- A matched backup restores successfully into isolated staging before any live
  cutover.

## Delivery Tracks

This platform is delivered through four coordinated plans rather than one
monolithic implementation:

1. **Shared contracts and read-only viewer packages** in Homelab Inventory.
2. **Local sharing identity, privacy preview, publication client, and settings**
   in Homelab Inventory.
3. **Private `HomelabInventoryShare` service**, including ingestion, viewer,
   storage, identity, lifecycle, analytics, abuse reporting, and deployment.
4. **Coordinated rollout**, including package publication, contract gating,
   SkyBolt deployment, live end-to-end proof, backup/restore proof, and public
   documentation.

Each track must produce independently testable software and must not weaken the
privacy or compatibility boundary to accelerate rollout.
